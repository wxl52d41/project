# 第三方调用方接入指南

面向**调用方（第三方开发者 / 插件 / 外部系统）**。我方作为服务方提供接口并校验 API Key，你方申请 Key 后携带调用。

- 服务地址示例：`http://localhost:8090`（以实际分配为准）
- 调试台：`http://localhost:8090/debug.html`（可视化创建 / 编辑 / 一键调用）
- 姊妹文档：[接入手册](接入手册.md)（服务方视角）· [技术设计手册](技术设计手册.md)

## 一、如何申请 Key

### 1.1 申请流程

实际场景存在两种申请模式（市场真实做法）：

**模式 A：平台审批模式**（高德 / 微信开放平台式，适合企业对接）：

```
1. 第三方提交申请：调用方身份、用途（title）、需要的 scope 权限
2. 我方管理员审批（申请单处于「审批中」，Key 已生成但被禁用，调用返回 12303）
3. 审批通过：Key 即刻可用（isValid=true）
4. 审批驳回：申请单作废（Key 删除）
5. Key 通过安全渠道交付（线下 / 加密邮件，不走明文 HTTP / IM）
```

示例环境提供了完整审批流接口（详见 1.3 与第四章快速开始）：

| 接口 | 角色 | 说明 |
|------|------|------|
| `/applyApiKey` | 第三方 | 提交申请（创建即禁用，extraData 记录申请状态与理由） |
| `/admin/pendingList` | 管理员 | 查看待审批列表 + 历史记录 |
| `/admin/approve` | 管理员 | 审批通过（isValid=true，即刻可用） |
| `/admin/reject` | 管理员 | 驳回（申请单删除作废） |

**模式 B：用户自助模式**（OpenAI / Kimi / 阿里云百炼式，适合插件代替用户操作）：

```
1. 用户登录我方系统
2. 在「API Key 管理」页面自助创建（Key 绑定用户 loginId，即刻可用）
3. 用户自选 scope，可随时自行吊销
```

两种模式的判断标准——**授权主体是谁**：Key 代替某个用户操作用模式 B；Key 代替一家企业调接口用模式 A。两种模式可并存（示例环境同时保留 `/applyApiKey` 审批流与 `/createApiKey` 自助创建）。

### 1.2 申请时需要确认的信息

| 项 | 示例 | 说明 |
|----|------|------|
| 调用方身份 | 头像同步插件 | 对应 Key 的 `title`，便于审计 |
| 绑定账号 | loginId 10001 | Key 归属的用户，一个用户可持多个 Key |
| 需要的 scope | `userinfo`、`avatar` | 按最小化原则申请，只给业务必需的权限 |
| 有效期 | 30 天（默认）/ 自定义 / 永久 | 建议短周期 + 定期轮换 |

### 1.3 提交申请（示例环境）

示例环境两种模式都开放（生产环境按 1.1 走对应流程）：

```bash
# 模式 A：平台审批流（提交后处于审批中，调用返回 12303，需管理员审批）
curl "http://localhost:8090/applyApiKey?loginId=10001&applyReason=ERP对接拉取订单&scopes=userinfo,chat"

# 模式 B：用户自助创建（即刻可用）
curl "http://localhost:8090/createApiKey?loginId=10001"
```

审批流响应（模式 A）：

```json
{
  "code": 200,
  "data": {
    "title": "申请审批中",
    "apiKey": "AK-Nks8V0yHjz6veZJa1YmbpiJt49lUJgIJRCJa",
    "loginId": "10001",
    "isValid": false,
    "scopes": ["userinfo", "chat"],
    "extraData": { "applyStatus": "PENDING", "applyReason": "ERP对接拉取订单" }
  }
}
```

管理员审批：

```bash
# 查看待审批列表
curl "http://localhost:8090/admin/pendingList?loginId=10001"

# 审批通过（Key 即刻可用）
curl "http://localhost:8090/admin/approve?apiKey=AK-xxx&approvedBy=admin-zhang"

# 驳回（申请单作废）
curl "http://localhost:8090/admin/reject?apiKey=AK-xxx&approvedBy=admin-zhang"
```

> 生产环境不会开放自助创建与审批接口，请走申请流程或管理后台。`AK-` 前缀是约定标识（便于 secret 扫描工具识别泄露）。

### 1.4 Key 的生命周期

| 阶段 | 说明 |
|------|------|
| 交付 | 仅创建时完整显示一次 |
| 使用 | 携带调用（见第二章），过期前有效 |
| 轮换 | 过期前申请新 Key → 切换 → 吊销旧 Key（避免服务中断） |
| 吊销 | 泄露或停止合作时立即删除，秒级生效、全实例同步 |
| 过期 | 超过 `expiresTime` 自动失效（返回 12302），需重新申请 |

## 二、如何携带 Key 调用

### 2.1 两种传参方式（任选其一）

| 方式 | 格式 |
|------|------|
| ① query 参数 | `/akRes1?apikey=AK-xxx` |
| ② 请求头 | `apikey: AK-xxx`（全小写） |

```bash
# 方式一：query 参数
curl "http://localhost:8090/akRes1?apikey=AK-KsvKA7FxkUrRJkKm4rjj3daIyWxh8Fc9wrBb"

# 方式二：请求头
curl -H "apikey: AK-KsvKA7FxkUrRJkKm4rjj3daIyWxh8Fc9wrBb" http://localhost:8090/akRes1
```

Java 调用示例：

```java
// query 方式
String url = "http://localhost:8090/akRes2?apikey=" + URLEncoder.encode(apiKey, "UTF-8");
HttpURLConnection conn = (HttpURLConnection) new URL(url).openConnection();
conn.setRequestProperty("apikey", apiKey);   // 或 header 方式（二选一即可）
```

> 参数名固定为 `apikey`（全小写）。两种方式等价，query 优先级高于 header。

### 2.2 scope 权限

不同接口要求的 scope 不同，由我方在接口上声明：

| 接口 | 要求 | 说明 |
|------|------|------|
| `/akRes1` | 仅需有效 Key | 无 scope 要求 |
| `/akRes2` | `userinfo` | 单一 scope |
| `/akRes3` | `userinfo` **且** `chat` | AND 模式（全部具备） |
| `/akRes4` | `userinfo` **或** `chat` | OR 模式（其一即可） |

你的 Key 必须具备接口要求的全部（或其一）scope，否则返回 12311。**申请时按需索权，不要申请用不到的权限**——这也便于我方审计。

### 2.3 完整调用演示

```bash
KEY="AK-KsvKA7FxkUrRJkKm4rjj3daIyWxh8Fc9wrBb"

# 1. 无 scope 要求的接口 → 200
curl "http://localhost:8090/akRes1?apikey=$KEY"
# {"code":200,"loginId":"10001","scopes":[],"title":"test"}

# 2. 需要 userinfo scope，但 Key 未授权 → 401 / 12311
curl "http://localhost:8090/akRes2?apikey=$KEY"
# {"code":12311,"apiKey":"AK-...","message":"该 API Key 不具备 Scope：userinfo"}

# 3. 向我方申请加上 userinfo,chat scope 后 → 200
curl -H "apikey: $KEY" http://localhost:8090/akRes2
# {"code":200,"loginId":"10001","scopes":["userinfo","chat"],...}
```

### 2.4 错误码与自查

| code | HTTP | 含义 | 你方自查方向 |
|------|------|------|------------|
| 12301 | 401 | 无效 Key | Key 拼写错误 / 已被删除 / 尚未生效 |
| 12302 | 401 | 已过期 | 申请续期或重新申请；定期轮换避免此问题 |
| 12303 | 401 | 已被禁用 | 联系我方确认（可能是泄露后被我方主动吊销） |
| 12311 | 401 | 不具备 Scope | 对照 2.2 确认接口要求，向 我方申请补授权 |
| 12312 | 401 | 不属于该用户 | 用错了 Key（每个 Key 绑定唯一账号） |

### 2.5 安全注意事项

1. **Key 等同于密码**：不要提交到 Git 仓库、不要写入前端 / 移动端代码、不要出现在日志里
2. **环境变量存储**：`API_KEY=AK-xxx`，代码从环境变量读取
3. **泄露立即上报**：我方秒级吊销（全实例同步），并为你签发新 Key
4. **不要共享 Key**：一个插件 / 用途一个 Key，出问题可精准吊销不影响其他
5. **资金 / 订单类接口**：API Key 只解决"你是谁"，敏感报文我方另行要求接口签名（防篡改 / 防重放），届时按签名文档接入

## 三、API Key 模式的真实市场案例

以下是市场上面向**第三方调用方**的 API Key 真实用法（均为各平台公开文档内容），你方接入时遇到的概念与行为与它们完全同构。

### 3.1 OpenAI API Key —— 最典型的 Bearer 调用

```bash
curl https://api.openai.com/v1/models \
  -H "Authorization: Bearer sk-xxx"
```

- Key 在控制台自助创建，**仅创建时完整显示一次**（与本组件 1.3 行为一致）
- 可设置过期日期、按项目分 Key、随时吊销
- 官方安全建议（与本手册 2.5 完全同源）：严禁入库、严禁前端部署、环境变量存储、泄露立即轮换

### 3.2 GitHub Personal Access Token —— Scope 授权的标杆

GitHub 支持两种 PAT，其 scope 粒度演进正是本组件 `scopes` 字段的设计参照：

| 类型 | scope 粒度 | 对应本组件 |
|------|-----------|-----------|
| classic | 粗粒度（`repo` / `user` / `write:org`…） | `addScope("repo")` |
| fine-grained | 细到"某个仓库的只读权限" | scope 命名空间化（演进方向） |

调用方式（`token` 前缀 + header，与本组件 `apikey` header 同构）：

```bash
curl -H "Authorization: Bearer ghp_xxx" https://api.github.com/user
```

关键行为一致点：**token 与用户绑定**——用户失去资源访问权，token 自动失效（对应本组件 Key 绑定 loginId、`checkApiKeyLoginId` 校验归属）。

### 3.3 PyPI / npm 发布 token —— 前缀标识 + 平台侧泄露检测

```
pypi-AgEIcHlwaS5vcmc...(85+ 字符)
npm_xxxxxxxxxxxxxxxx
```

- **前缀标识**是行业惯例：`pypi-` / `npm_` / `ghp_` / `sk-` / 本组件的 `AK-`——目的是让 GitGuardian 等扫描工具能从代码库里识别出泄露的凭证
- PyPI 官方与 GitHub 联动：检测到公网泄露的 token **自动吊销**，第三方（deps.dev 等）可通过 API 上报泄露
- 发布场景专用（CI 里上传包），最小化授权的典型实践：一个发布通道一个 token

### 3.4 真实反面教材：Key 为什么不能随意保管

近年公开的供应链攻击（GitGuardian / BleepingComputer 报道）：

| 事件 | 手法 | 后果 |
|------|------|------|
| 假 Paysafe/Skrill SDK（npm/PyPI 17 个恶意包） | 恶意依赖扫描环境变量中的 API key 回传攻击者服务器 | Paysafe / AWS / GitHub 凭证批量失窃 |
| GhostAction 供应链攻击 | 恶意 GitHub Actions workflow 窃取 PyPI 发布 token | PyPI 官方批量吊销全部被盗 token，570+ 仓库紧急告警 |
| 48 小时三连击（npm/PyPI/Docker Hub） | 恶意包专扫 `KEY/SECRET/TOKEN/PASS/AUTH` 环境变量 | 开发者环境与 CI 凭证大规模失窃 |

**这些攻击全部针对"Key 明文存放在环境变量 / 配置文件"的场景**——这正是 2.5 安全注意事项的由来。API Key 是 Bearer 凭证（谁持有谁能用），泄露即失守，必须配合：短有效期、按用途分 Key、泄露秒级吊销。

### 3.5 API Key vs 会话 Token vs 接口签名（你该用哪种凭证）

| 凭证 | 适用场景 | 局限 |
|------|---------|------|
| **API Key（本组件）** | 长期服务间调用、插件代替用户操作 | 无法防篡改 / 防重放，泄露即失守 |
| 会话 Token | 用户浏览器会话 | 用户退出即失效，不适合第三方长期持有 |
| 接口签名（apiSign） | 资金 / 订单 / 回调通知 | 密钥不出现在请求里，抓包也无法伪造 |

市场通行做法是**叠加使用**：Stripe 的调用方向用 API Key（方便），平台回调方向用 HMAC 签名（安全）；阿里云 AccessKey 管身份、请求再叠加签名管报文完整性。你方向我方调用用 API Key；若涉及敏感报文，我方会另行提供签名接入文档。

## 四、快速开始（端到端示例）

```bash
BASE="http://localhost:8090"

# 1. 申请 Key（示例环境自助；生产走申请流程）
KEY=$(curl -s "$BASE/createApiKey?loginId=10001" | grep -o 'AK-[A-Za-z0-9]*')
echo "你的 Key: $KEY"

# 2. 携带调用（query 方式）
curl "$BASE/akRes1?apikey=$KEY"

# 3. 携带调用（header 方式）
curl -H "apikey: $KEY" $BASE/akRes1

# 4. 查询自己的 Key 列表（确认有效期 / scope）
curl "$BASE/myApiKeyList?loginId=10001"

# 5. 停止使用时吊销
curl "$BASE/deleteApiKey?apiKey=$KEY&loginId=10001"

# 6. 吊销该账号全部 Key（换账号 / 全面停止合作时）
curl "$BASE/deleteMyAllApiKey?loginId=10001"
```

浏览器访问 `http://localhost:8090/debug.html` 可视化完成以上全部操作。调试台顶部可切换两种模式：

- **A · 审批模式**：A1 第三方提交申请 → A2 管理员审批（通过 / 驳回）→ A3 已审批 Key 调用测试
- **B · 免审批模式**：B1 用户自助创建（即刻可用）→ B2 编辑 scope / 有效期 / 状态 → B3 调用测试
