> 姊妹组件：[apiSign 接口签名组件](../../apiSign)（API Key 管账号体系，签名管报文安全，两者常叠加使用）。

---

## 一、设计目标与边界

| 目标 | 实现方式 |
|------|---------|
| 不依赖 sa-token | 从 `sa-token-apikey` 拷贝改造，`SaTokenDao + SaSession` 组合抽象为 `ApiKeyStore` 接口 |
| 零依赖核心层 | `api-key-core` 仅依赖 JDK，可直接打进任意客户端 / SDK |
| 服务方引入即生效 | `spring.factories` 自动装配，零注解 |
| 凭证生命周期管理 | 创建 / 查询 / 修改 / 禁用 / 删除 / 按用户批量回收 |
| Scope 最小化授权 | `@ApiKeyCheck(scope = {...})`，AND / OR 两种模式 |
| 多实例天然共享 | 存储固定使用 Redis 实现 `RedisApiKeyStore` |

**不做的事**：不做报文防篡改（那是 apiSign 的职责）、不做业务幂等、不自带全局异常处理器、不支持非 Servlet 栈。

## 二、需求场景与市场对标（真实案例）

### 2.1 为什么需要 API Key（设计原点）

典型场景（源自 sa-token 官方文档的论坛故事）：第三方为你的网站开发插件（自动换头像、自动发帖、粉丝通知……），用户必须给插件一个"凭证"才能代替自己调用 API。不同凭证的后果：

| 提供的凭证 | 后果 |
|-----------|------|
| 账号密码 | 插件得到账号全部权限，安全风险极高 |
| 会话 token | 几乎所有 API 权限，且用户退出登录即失效 |
| **API Key** | **可控范围内部分授权（Scope），随时取消，按需设有效期** |

API Key 的五个特征：随机字符串格式、与 loginId 绑定（可追溯授权人）、一个用户可持多个（不同插件各一个）、每个 Key 独立 Scope（最小化授权）、可设有效期随时回收。

### 2.2 市场真实案例（API Key 模式）

| 平台 | 做法 | 与本组件的对应关系 |
|------|------|------------------|
| **OpenAI API Key** | `Authorization: Bearer sk-xxx`，无签名无时间戳 | Bearer 模式；官方最佳实践承认全部结构性风险，全靠管理手段补救（见 2.3） |
| **GitHub PAT (classic)** | 粗粒度 scope（`repo` / `user`…） | 对应 `ApiKeyModel.scopes` + `@ApiKeyCheck(scope=...)` |
| **GitHub fine-grained PAT** | 细到"某仓库的只读权限"；与用户绑定，用户失去资源访问权 token 自动失效 | 对应 `checkApiKeyLoginId`（Key 与 loginId 绑定）；细粒度是本组件 Scope 体系的演进方向 |
| **PyPI / npm 发布 token** | `pypi-xxx`、`npm_xxx` 前缀标识 + 平台侧扫描撤销 | 前缀标识对应 `prefix: AK-`（便于 secret 扫描工具识别泄露） |

### 2.3 反面教材：API Key 的结构性风险（真实安全事件）

| 事件 | 手法 | 后果 |
|------|------|------|
| 假 Paysafe/Skrill SDK（npm/PyPI 17 个恶意包） | 恶意包扫环境变量里的 API key 回传 C2 | Paysafe API key、AWS key、GitHub token 被窃 |
| GhostAction 供应链攻击 | 恶意 GitHub Actions workflow 窃取 PyPI 发布 token | PyPI 官方**批量吊销**全部被盗 token，570+ 仓库告警 |
| 48 小时三连击（npm/PyPI/Docker Hub） | 专扫 `KEY/SECRET/TOKEN/PASS/AUTH` 环境变量 | 开发者环境与 CI 凭证大规模失窃 |

**结论**：静态明文 Bearer 凭证"泄露即失守"，只能靠管理手段止损。OpenAI 官方最佳实践的全部建议——每成员独立 Key、强制过期 + 定期轮换、严禁入库 / 入前端、支出硬限额、公网检测到即禁用——本质都是在给这个结构性弱点打补丁。本组件照单落实为工程能力：

| OpenAI 建议 | 本组件对应 |
|------------|-----------|
| 每成员 / 每用途独立 Key | 一个 loginId 可创建多个 Key，各自命名（title） |
| 强制过期 + 轮换 | `expiresTime`（默认 30 天，-1 永久）、随时删除重建 |
| 可随时撤销 | `deleteApiKey` / `deleteApiKeyByLoginId`（按用户批量回收） |
| 最小权限 | `scopes` + `@ApiKeyCheck` 注解校验 |
| 泄露可检测 | `prefix: AK-` 前缀可被 secret 扫描工具识别 |

### 2.4 与接口签名（apiSign）的分工

生产上两种模式常叠加（Stripe：调用方向用 API Key、webhook 回调用 HMAC 签名；阿里云：AK 管身份 + 请求签名管报文）：

| 维度 | 本组件（API Key） | apiSign（接口签名） |
|------|------------------|-------------------|
| 回答的问题 | 你是谁、能干什么（身份 + 授权） | 报文是否被篡改 / 重放（完整性） |
| 凭证形态 | Key 明文随请求传输（Bearer） | secretKey 永不出现在请求里 |
| 泄露后果 | 拿到即可冒用，直到吊销 | 抓包无效（造不出签名） |
| 防篡改 / 防重放 | ❌ | ✅ |
| 生命周期管理 / Scope | ✅ | 弱（只有 enabled / appIds） |

## 三、模块划分

```
api-key-parent
├── api-key-core                 零 Spring 依赖：模型、算法、存储接口
├── api-key-spring-boot-starter  验签端：注解 + 拦截器 + Redis 存储 + 自动装配
└── api-key-sample               示例应用 + /debug.html 调试台
```

| 类 | 模块 | 职责 |
|----|------|------|
| `ApiKeyModel` | core | 凭证模型（title/intro/apiKey/loginId/createTime/expiresTime/isValid/scopes/extraData） |
| `ApiKeyTemplate` | core | 全部业务操作：创建 / 保存 / 查询 / 校验 / Scope / 归属 / 索引维护 |
| `ApiKeyStore` | core | 存储接口（6 方法：模型 CRUD + 索引读写） |
| `ApiKeyConfig` | core | prefix / timeout / isRecordIndex |
| `ApiKeyException` / `ApiKeyScopeException` | core | 异常（含 apiKey / scope 上下文，链式 set 不断链） |
| `ApiKeyErrorCode` | core | 12301-12312，码值与 sa-token-apikey 保持一致 |
| `ApiKeyDataLoader` | core | DB 直查接口（预留，见 7.2） |
| `ApiKeyCheck` / `ApiKeyCheckInterceptor` | starter | 注解（scope + AND/OR）与拦截器 |
| `RedisApiKeyStore` | starter | 唯一默认存储实现 |
| `ApiKeyProperties` / `ApiKeyAutoConfiguration` | starter | 配置绑定与自动装配 |

## 四、核心设计

### 4.1 凭证生成

```
apiKey = prefix("AK-") + 36 位随机串（SecureRandom）
```

- 密码学安全随机（`SecureRandom`，不可预测是防伪造的根基）
- 生成后存在性检查防碰撞（重试上限 100 次）
- 创建入口：`createApiKeyModel()`（仅生成）/ `createApiKeyModel(loginId)`（同时补全有效期与状态），补全 title/scopes 后 `saveApiKey` 持久化（含索引维护）

### 4.2 校验链路

```
checkApiKey:
  ├─ getApiKey == null          → 12301 无效
  ├─ timeExpired()              → 12302 已过期
  └─ !isValid                   → 12303 已禁用

checkApiKeyScope（AND）/ checkApiKeyScopeOr（OR）:
  └─ scopes 不包含              → 12311（ApiKeyScopeException，带 scope 上下文）

checkApiKeyLoginId:
  ├─ 模型不存在                 → 12301
  └─ String.valueOf(loginId) 不等 → 12312（10001 与 "10001" 视为同一用户，与 sa-token 口径一致）
```

### 4.3 主要查询 API

| 方法 | 说明 |
|------|------|
| `getApiKey(String)` | 查模型，无效返回 null |
| `getLoginIdByApiKey(String)` | 校验通过后返回授权人 loginId |
| `getApiKeyList(Object)` | 按用户查全部 Key（依赖索引，未开启返回空列表） |
| `isApiKeyLoginId(String, Object)` / `hasApiKeyScope(...)` | 不抛异常版校验（返回 boolean） |

### 4.4 存储设计（Redis）

固定使用 Redis，key 结构：

| 数据 | key | value | TTL |
|------|-----|-------|-----|
| 凭证模型 | `api-key:model:{apiKey}` | JSON | 剩余有效期（-1 不设 TTL） |
| 用户索引 | `api-key:index:{loginId}` | JSON 数组（该用户全部 apiKey） | 名下最长有效 Key 的有效期 |

要点：

- **索引 TTL 对齐**（`calcIndexTtl`）：索引若比 Key 先过期，`getApiKeyList` 会漏查；略长无害（下次 save / adjustIndex 重新对齐）
- **saveApiKey 对已过期 Key 直接删除**（存储层 TTL 双保险，与 sa-token 行为一致）
- **序列化副本**：存取均走 JSON，业务代码拿到的是副本，防绕过 `saveApiKey` 自检直接改字段
- **`-1` 永不过期不设 TTL**，与 `NEVER_EXPIRE` 语义对齐

### 4.5 索引维护

- 保存：并入用户索引列表 + TTL 对齐
- 删除单个：移出索引；列表空则删索引记录
- `deleteApiKeyByLoginId`：遍历索引删模型，再删索引（未开启索引时抛 12305）
- `adjustIndex(loginId)`：清理过期 Key 的索引残留 + TTL 重新对齐

### 4.6 请求取值

`ApiKeyCheckInterceptor` 取值顺序：**query 参数 `apikey` → 请求头 `apikey`**（全小写）。与 sa-token 版差异：去掉了 Authorization Basic 兜底（用法罕见），多账号命名空间（namespace）暂未实现（见 8 限制）。

### 4.7 控制器读取的正确姿势

```java
// ✅ 正确：与拦截器一致的 param → header 回退
String apikey = request.getParameter("apikey");
if (apikey == null || apikey.isEmpty()) {
    apikey = request.getHeader("apikey");
}

// ❌ 错误：String apikey 形参只从 query 绑定，header 方式拿到 null
public SaResult akRes1(String apikey) { ... }
```

## 五、错误码

| code | 含义 | 触发位置 |
|------|------|---------|
| 12301 | 无效 API Key | checkApiKey / checkApiKeyLoginId / 异常默认码 |
| 12302 | API Key 已过期 | checkApiKey |
| 12303 | API Key 已被禁用 | checkApiKey |
| 12304 | 字段自检未通过（缺 apiKey/loginId/createTime/expiresTime/isValid） | checkByCanSaved |
| 12305 | 未开启索引记录却调用索引相关 API | deleteApiKeyByLoginId |
| 12311 | 不具备指定 Scope | checkApiKeyScope(Or) |
| 12312 | 不属于指定用户 | checkApiKeyLoginId |

HTTP 映射由宿主异常处理器决定（sample 中统一转 401）。

## 六、自动装配

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnWebApplication(type = SERVLET)
@ConditionalOnProperty(prefix = "api.key", name = "enabled", matchIfMissing = true)
```

- `apiKeyStore`：**固定返回 `RedisApiKeyStore`**（`@ConditionalOnMissingBean`，宿主注册自定义 Store 即覆盖）
- `apiKeyTemplate` / `apiKeyCheckInterceptor`：同样可覆盖
- 拦截器注册 `/**`，未标注 `@ApiKeyCheck` 的接口直接放行
- Redis 依赖为**正式依赖**（非 optional）——存储唯一实现所需，宿主无需单独引入

## 七、扩展点

### 7.1 自定义存储

注册同类型 Bean 覆盖（如换 DB）：

```java
@Bean
public ApiKeyStore apiKeyStore(DataSource dataSource) {
    return new JdbcApiKeyStore(dataSource);
}
```

### 7.2 数据库模式（缓存 miss 回源）

`ApiKeyDataLoader` 接口已定义（`getApiKeyModelFromDatabase`），**当前未在 `ApiKeyTemplate` 内接线**——本组件的取舍是"Store 即唯一事实源"，Redis 即持久层。若业务要"Redis 缓存 + DB 持久"双层，建议直接实现组合版 `ApiKeyStore`（写双写、读回源），比 sa-token 的 DataLoader 模式（索引职责随之外移）更内聚。

### 7.3 申请-审批流（平台审批模式）

对标高德 / 微信开放平台的审批型接入。**基于现有字段实现，core 零改动**——状态机：

```
第三方提交申请（/applyApiKey）
  → isValid=false + extraData{applyStatus=PENDING, applyReason=...}
  → 审批中调用返回 12303（语义完全吻合「审批中不可用」）

管理员审批通过（/admin/approve）
  → isValid=true + extraData{applyStatus=APPROVED, approvedBy=...}
  → Key 即刻可用（全实例生效）

管理员驳回（/admin/reject）
  → deleteApiKey（申请单作废，Key 永不可用）
```

**为什么用 `isValid` + `extraData` 而不新建申请表**：审批中的 Key 与正式 Key 的唯一差异是"是否放行"，`isValid=false` 精确表达这一状态且复用全部现有校验链路（checkApiKey 的 12303 分支）；申请理由、审批人等审计信息属于 Key 的扩展属性，`extraData` 正是为此设计。需要正式的申请单号 / 审批记录 / 驳回原因回显时才值得建表，示例实现（`ApiKeyAdminController`）已覆盖 90% 场景。

**与用户自助模式的并存**：OpenAI 式自助创建（`createApiKeyModel` + 立即 `isValid=true`）与审批流并存——由宿主决定开放哪种入口，互不干扰。

**已知限制**：审批接口（`/admin/*`）在示例中未做管理员鉴权，生产接入时必须叠加（登录态 + 管理员角色校验），否则任何人都能审批自己的申请。

## 八、已知限制

| # | 限制 | 说明 |
|---|------|------|
| L1 | 多账号体系（namespace）未实现 | sa-token 支持 `new SaApiKeyTemplate("admin-apikey")` 隔离 Admin/User 两套；本组件单命名空间，需要时给 Store 的 key 加前缀实现 |
| L2 | Key 明文存储于 Redis | 泄露 Redis 即泄露全部凭证；高安全场景可考虑哈希存储（存 SHA-256(apiKey)，查询侧哈希后比对） |
| L3 | 无调用量限制 | OpenAI 的"支出限额"类能力需宿主自行埋点实现（extraData 可存配额元信息） |
| L4 | 不支持 Authorization Basic 传递 | sa-token 支持第三种取值方式，本组件只保留 query / header 两种 |
| L5 | 索引读改写非原子 | 并发下两个请求同时改同一用户索引可能互相覆盖（低概率，影响仅限列表展示，不影响校验） |

## 附录：与 sa-token-apikey 的差异清单

| 项 | sa-token-apikey | 本组件 |
|----|----------------|--------|
| 存储 | SaTokenDao + SaSession（跟随 sa-token 全局存储） | ApiKeyStore 接口，固定 Redis 实现 |
| 数据加载 | SaApiKeyDataLoader（缓存 miss 回源 DB） | 接口保留，未接线（见 7.2） |
| 取值 | param → header → Authorization Basic | param → header |
| 多账号 | namespace 隔离 | 未实现（L1） |
| 索引 | RawSession + adjustIndex TTL 对齐 | 独立索引 key + calcIndexTtl 对齐（语义一致） |
| 依赖 | sa-token-core | 零依赖（core 仅 JDK） |
