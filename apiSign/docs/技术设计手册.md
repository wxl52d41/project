# API 签名验签组件 — 技术设计手册

> 内部技术文档。读者为组件维护者与集成方研发。
> 对外接入说明见 [第三方接入文档](第三方接入指南.md)。

---

## 一、设计目标与边界

| 目标 | 实现方式 |
|------|---------|
| 不依赖 sa-token | 算法层自行实现 `DigestUtils` / `SignTemplate`，仅用 JDK |
| 算法与 sa-token-sign 逐字节一致 | 用官方单测锚点校验（见 [3.4](#34-算法锚点)） |
| 同时支持 query/form 与 JSON body | `SignParamResolver` 按 Content-Type 分流 |
| 服务方可直接引入生效 | `spring.factories` 自动装配，零注解 |
| 调用方只需算法层 | `api-sign-core` 零 Spring 依赖 |
| 密钥可换源 | `AppSecretProvider` 接口 + `@ConditionalOnMissingBean` |
| 多实例可扩展 | `NonceStore` 接口 + 原子写入语义 |

**不做的事**：不做业务幂等、不做权限模型、不自带全局异常处理器、不支持非 Servlet 栈（WebFlux）。

## 三、签名算法设计

### 3.1 口径定义

```
paramsStr = 全部参与参数（含 timestamp、nonce，不含 sign）
            按 key 字典序升序 拼成 k1=v1&k2=v2

HMAC 系列：  sign = HMAC(secretKey, paramsStr)
非 HMAC：    sign = digest(paramsStr + "&key=" + secretKey)
输出：       小写十六进制
```

### 3.2 实现要点

```
SignTemplate.createSign(paramsMap, app)
  ├─ new TreeMap<>(paramsMap)      // 字典序，不污染入参
  ├─ paramsMap.remove("sign")      // 排除 sign
  ├─ joinParamsDictSort()          // 拼 k=v&k=v
  ├─ isHmac(app) ? paramsStr
  │               : paramsStr + "&key=" + secretKey
  └─ dispatchDigest(algo, key, fullStr)
```

**关键约束**：`TreeMap` 保证排序确定性；非 HMAC 的 `&key=` 必须是 `&` 连接（sa-token 口径），不是 `key=`。

### 3.3 算法分发

```
dispatchDigest(algo, key, fullStr)
  md5 | sha1 | sha256 | sha384 | sha512   → DigestUtils.digest(fullStr, algo)
  hmac-md5 | hmac-sha256 | hmac-sha512    → DigestUtils.hmacDigest(key, data, algo)
  default                                  → SignException(12205)
```

判断 HMAC 用 `digestAlgo.toLowerCase().startsWith("hmac-")`，新增 HMAC 算法自动归类。

### 3.4 算法锚点

单测锚点用于证明与 sa-token-sign 互通，改动算法层必须保持通过：

| 场景 | 期望值 |
|------|--------|
| `{name:zhang, age:18, sex:女}` + md5 + key=`SwqFmsKxcbq23` | `6f5e844a53e74363c2f6b24f64c4f0ff` |
| 同上 + hmac-sha256 | `f2cb11bddf000a4c71f8bd280cab65a84d99f1b4c490a6fbbbe49fffec7203cb` |
| 同上 + hmac-md5 | `269c49e0541d24e9732895db2af7944d` |
| `{name:nzxy, age:18, timestamp:1740000000000, nonce:abc}` + sha256 | `a96f90e704815d850a4ff0308e3b165f3ee6f65171280d6b71dd6b28b0a5b826` |

### 3.5 JSON 展平设计

服务端的 `flattenJsonNode(JsonNode,...)` 与客户端的 `SignClient.flatten(...)` 必须产生**相同的键值对**，否则两端签名不一致。

| JSON | 键 | 值来源 |
|------|-----|--------|
| 对象 | `prefix.key` | 递归 |
| 数组 | `prefix[i]` | 递归 |
| 标量 | `prefix` | `node.asText()` / `String.valueOf()` |
| `null` | — | 跳过 |

**值字符串化的口径风险**：服务端用 Jackson `asText()`，客户端用 `String.valueOf()`。两者对 `int`/`String`/`boolean` 一致（`true` → `"true"`），但 **BigDecimal 精度**与 **Date 类型**行为不同。因此客户端约定只传 `Map`/`List`/基本类型，POJO 需先转 Map。

### 3.6 深度保护

`MAX_FLATTEN_DEPTH = 32`，超限抛 12206。防的是恶意构造超深 JSON 触发 `StackOverflowError`（`StackOverflowError` 是 `Error` 不是 `Exception`，无法被 `catch (Exception)` 捕获，会直接打挂线程）。

## 四、验签链路源码分析

### 4.1 调用链

```
HTTP 请求
  │
  ├─ RepeatableReadFilter (Order = HIGHEST_PRECEDENCE)
  │    ├─ isJsonBody? 否 → 直接 doFilter，原请求
  │    └─ 是 → new RepeatableReadRequestWrapper(request)  // 构造时缓存 body
  │              └─ 超 2MB → SignException(12206) → Filter 内直接写响应（不经全局异常处理器）
  │
  ├─ DispatcherServlet → HandlerMapping → HandlerExecutionChain
  │
  ├─ ApiSignInterceptor.preHandle
  │    ├─ handler 非 HandlerMethod → return true
  │    ├─ 取 @ApiSign（方法优先，其次类）
  │    ├─ 无注解 → return true
  │    ├─ 1. appId = header(appIdHeader) ?: param("appId")  → 空 → 12207
  │    ├─ 2. appSecretProvider.getApp(appId)                → null → 12208
  │    │     app.isEnabled()                                 → false → 12209
  │    ├─ 3. apiSign.appIds() 非空 && 不含 appId             → 12210
  │    ├─ 4. signParamResolver.resolve(request, includeParams)
  │    └─ 5. signTemplate.checkParamMap(paramMap, app)
  │
  └─ Controller → @RequestBody 读取（Wrapper 返回新流，不受验签影响）
```

### 4.2 SignParamResolver.resolve 分解

```
resolve(request, includeParams)
  1. getSignParam(request)
       ├─ 非 JSON：遍历 request.getParameterMap()，每个 key 取 values[0]
       └─ JSON  ：读 body → objectMapper.readTree
                    ├─ root 非 object → 12206
                    ├─ flattenJsonNode(..., depth=0) → 12206（超深）
                    └─ IOException → 12206
  2. putPathVariables(request, paramMap)
       从 HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE 取 URI 模板
       逐段比对，{var} / {var:regex} 取出变量名，取 path 对应段
       UriUtils.decode(value, UTF_8) 后并入
  3. JSON 模式下把 header 的 timestamp/nonce/sign 并入
  4. includeParams 非空 → retainAll(白名单 ∪ 三件套)
```

**三个易错点**：

1. **路径参数**不在 `getParameterMap()` 里，必须单独解析。否则 `/order/123` 改成 `/order/456` 签名依然通过。
2. **白名单必须保留三件套**，否则 `retainAll` 把 timestamp/nonce/sign 也删了，导致必然 12204。
3. **必须用独立 `ObjectMapper`**（`new ObjectMapper()`），不能注入宿主的。宿主可能配置了 `BigDecimal`→`String`、`FAIL_ON_NULL` 等策略，会让展平口径漂移，导致客户端与服务端算出的签名不一致。

### 4.3 checkParamMap 内部顺序

```
checkParamMap(paramMap, app)
  ├─ 三件套非空（notEmpty × 3）        → 12204
  ├─ checkTimestamp(parseTimestamp(v))  // 非数字 → 12204，超窗 → 12203
  ├─ checkNonce(nonce, app)             // setIfAbsent 失败 → 12202
  └─ checkSign(paramMap, sign, app)     // 不一致 → 12202
```

**顺序设计权衡**：nonce 在签名比对**之前**登记。虽然存在"nonce 被浪费"的副作用（签名算错的请求也消耗 nonce），但换来的是**无法通过构造非法签名来探测 nonce 是否被使用**。反过来（先验签名再登记 nonce）则会让攻击者绕过防重放。当前顺序是安全优先的选择。

### 4.4 时间窗与 nonce TTL 的关系

| 项 | 公式 | 默认值（disparity=15min） |
|----|------|--------------------------|
| 时间窗 | `timestampDisparity` | 900000 ms |
| nonce TTL | `timestampDisparity / 1000 * 2 + 2` | 1802 s |
| disparity = -1 | 不校验时间窗，TTL 取 | 86400 s |

**TTL 取 2 倍 + 2 秒的原因**：nonce 记录必须比时间窗活得久。若 TTL = 时间窗，会出现"请求 timestamp 仍在窗口内，但 nonce 记录已过期"的窗口期，此时同一 nonce 可再次通过校验，防重放失效。2 倍是为了覆盖 `Math.abs` 的双向时间差。

### 4.5 nonce 存储键

```
"api-sign:nonce:" + appId + ":" + nonce
```

带 appId 的作用是**隔离命名空间**：不同接入方恰好生成相同 nonce 时不互相干扰。

## 五、可重复读设计

### 5.1 为什么需要

验签要读一次 body，`@RequestBody` 又要读一次。Servlet 的 `InputStream` 是一次性的，第二次读到 EOF 会得到空 body。

### 5.2 实现要点

```
RepeatableReadRequestWrapper
  ├─ 构造时：把 request.getInputStream() 全量读入 byte[]（限 2MB）
  ├─ getInputStream()：每次 new ByteArrayInputStream(body)
  ├─ getReader()：基于新的 getInputStream 包装，编码取 getCharacterEncoding() 默认 UTF-8
  └─ 覆写 available() / skip() / close() / isFinished() / isReady()
```

**必须覆写 `available()`**：Jackson 等库会用 `available()` 判断剩余长度，不覆写会拿到原始 request 的值（0 或错误值），导致解析失败。这是本组件开发期踩过的实际缺陷。

### 5.3 过滤器的两个保护

1. **只包装 JSON 请求**：`multipart/form-data` 文件上传若被全量读入内存，大文件直接 OOM。非 JSON 请求原样透传。
2. **防重复包装**：`request instanceof RepeatableReadRequestWrapper` 时跳过。宿主可能已用同类组件（如日志 body 打印）包装过，再包一层会导致 body 被重复消费。

### 5.4 Filter 内异常

Filter 执行早于 `DispatcherServlet`，`@RestControllerAdvice` 捕获不到。因此 `RepeatableReadRequestWrapper` 构造抛出的 12206 必须在 Filter 里手工写响应：

```java
response.setStatus(SC_BAD_REQUEST);
response.setContentType("application/json;charset=UTF-8");
response.getWriter().write("{\"code\":12206,\"message\":\"...\"}");
```

## 六、自动装配

### 6.1 装配条件

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnWebApplication(type = SERVLET)
@ConditionalOnProperty(prefix = "api.sign", name = "enabled", matchIfMissing = true)
@EnableConfigurationProperties(SignProperties.class)
public class ApiSignAutoConfiguration implements WebMvcConfigurer
```

| 条件 | 作用 |
|------|------|
| `spring.factories` 注册 | 引入即生效，无需 `@EnableXxx` |
| `SERVLET` | WebFlux（Reactor 栈）不装配，避免报错 |
| `api.sign.enabled` | `matchIfMissing = true` 默认开启；设 false 整体关闭 |
| `proxyBeanMethods = false` | 轻量模式，避免 CGLIB 代理开销 |

### 6.2 Bean 覆盖机制

全部核心 Bean 带 `@ConditionalOnMissingBean`，宿主注册同类型 Bean 即覆盖：

| Bean | 默认实现 | 覆盖场景 |
|------|---------|---------|
| `AppSecretProvider` | `PropertiesAppSecretProvider` | 密钥从 DB / 配置中心加载 |
| `NonceStore` | `MemoryNonceStore` | 多实例部署换 Redis |
| `SignTemplate` | `new SignTemplate(nonceStore)` | 极少，改算法口径时 |
| `SignParamResolver` | `new SignParamResolver()` | 自定义参数提取规则 |
| `ApiSignInterceptor` | 4 参构造 | 自定义拦截逻辑 |

`RepeatableReadFilter` **不带** `@ConditionalOnMissingBean`，因为它没有"同类型覆盖"语义，而是通过 `FilterRegistrationBean` 显式注册 + `setOrder`。

### 6.3 循环依赖处理

`ApiSignAutoConfiguration` 同时是"Bean 定义者"和"拦截器注册者"。若构造器直接注入自己 `@Bean` 的 `ApiSignInterceptor`，会形成自引用循环。解决方案：

```java
private final ObjectProvider<ApiSignInterceptor> interceptorProvider;

public ApiSignAutoConfiguration(SignProperties p, ObjectProvider<ApiSignInterceptor> ip) {
    this.interceptorProvider = ip;   // 延迟解析，addInterceptors 时才 getObject()
}
```

### 6.4 Filter 顺序

```java
registrationBean.setOrder(filterOrder == 0 ? Ordered.HIGHEST_PRECEDENCE : filterOrder);
```

必须早于任何读取 body 的 Filter（如日志、XSS 过滤），否则 body 在包装前被消费。配置 `api.sign.filter-order` 可调整。

## 七、扩展点

### 7.1 AppSecretProvider — 密钥来源

```java
@Bean
public AppSecretProvider appSecretProvider() {
    return appId -> {
        ThirdApp app = thirdAppMapper.selectByAppId(appId);   // 你的 DAO
        return app == null ? null
                : new SignApp(app.getAppId(), app.getSecretKey(), app.getDigestAlgo())
                        .setEnabled(app.getEnabled() == 1)
                        .setTimestampDisparity(app.getDisparity());
    };
}
```

**必须自行加缓存**。本接口在每次注解请求上被调用一次，直接查库会给每个请求加一次 DB 往返。建议 Caffeine 本地缓存 + 配置变更时主动失效。

未登记返回 `null`（不要抛异常），拦截器据此返回 12208。

### 7.2 NonceStore — 防重放存储

> 项目已内置 `RedisNonceStore`（当前 Bean 为注释状态），完整替换步骤见 [Redis-替换说明](Redis-替换说明.md)。

```java
@Bean
public NonceStore nonceStore(RedisTemplate<String, String> redis) {
    return new NonceStore() {
        @Override public String get(String k) { return redis.opsForValue().get(k); }
        @Override public void set(String k, String v, long ttl) {
            redis.opsForValue().set(k, v, ttl, TimeUnit.SECONDS);
        }
        @Override public boolean setIfAbsent(String k, String v, long ttl) {
            return Boolean.TRUE.equals(
                    redis.opsForValue().setIfAbsent(k, v, ttl, TimeUnit.SECONDS));
        }
    };
}
```

**`setIfAbsent` 必须是原子的**。这是整套防重放的安全根基：

| 错误实现 | 后果 |
|---------|------|
| `if (get(k) == null) { set(k, v); return true; }` | 并发下两个请求同时读到 null，都返回 true，防重放失效 |
| Redis `setIfAbsent` 未带 EX | key 永不过期，Redis 内存持续增长 |
| TTL 小于时间窗 | 窗口期内 nonce 记录过期，可重放（见 [4.4](#44-时间窗与-nonce-ttl-的关系)） |

### 7.3 默认内存实现的并发正确性

`MemoryNonceStore.setIfAbsent` 用 `ConcurrentHashMap.compute` 保证原子：

```java
Entry created = new Entry(value, expireAt);
Entry result = store.compute(key, (k, old) ->
        (old == null || old.expireAt < now) ? created : old);
return result == created;   // 引用相等：只有真正写入者拿到 true
```

`compute` 对同一 key 是原子操作，并发下仅一个线程能写入 `created`，其余拿到旧值。用**引用相等**而非 equals 判断，避免值相同的误判。

`CLEANUP_THRESHOLD = 1024`：条目超阈值触发一次全量扫描清理过期项。无后台线程，代价是清理时 O(n) 停顿（1024 量级可忽略）。

### 7.4 SignParamResolver — 自定义参数提取

覆盖场景：网关会加签某些 header 字段、需要把 URL 片段纳入签名等。

```java
@Bean
public SignParamResolver signParamResolver() {
    return new SignParamResolver() {
        @Override
        public Map<String, String> resolve(HttpServletRequest req, String... include) {
            Map<String, String> map = super.resolve(req, include);
            map.put("x-trace-id", req.getHeader("X-Trace-Id"));   // 网关字段也参与
            return map;
        }
    };
}
```

### 7.5 异常处理

组件**不自带** `@RestControllerAdvice`（避免与宿主已有的冲突）。宿主需自行处理 `SignException`：

```java
@RestControllerAdvice
public class SignExceptionHandler {
    @ExceptionHandler(SignException.class)
    public ResponseEntity<Map<String, Object>> handle(SignException e) {
        HttpStatus status = (e.getCode() == 12204 || e.getCode() == 12206 || e.getCode() == 12207)
                ? HttpStatus.BAD_REQUEST : HttpStatus.UNAUTHORIZED;
        return ResponseEntity.status(status)
                .body(Map.of("code", e.getCode(), "message", e.getMessage(), "data", null));
    }
}
```

注意 `Map.of` 是 Java 9+，Java 8 项目需用 `HashMap`。

## 八、已知限制与风险

### 8.1 安全相关

| # | 风险 | 影响 | 缓解 |
|---|------|------|------|
| R1 | **仅 timestamp + nonce 防重放** | nonce TTL 过期后同一请求报文可重放 | 缩短时间窗；业务侧仍需幂等键 |
| R2 | **nonce 空间隔离不彻底** | key 含 appId，但同一 appId 的多实例若用内存 store，各实例 nonce 空间独立 → **重放可在另一实例通过** | 多实例必须换 Redis 实现 |
| R3 | **签名不覆盖 header** | 除三件套外的 header（如 `X-User-Id`）不在签名内，可被篡改 | 敏感 header 需纳入签名（[7.4](#74-signparamresolver--自定义参数提取)） |
| R4 | **secretKey 明文存储** | YAML 明文、日志可能泄漏 | 配置中心加密、日志脱敏 |
| R5 | **非 HMAC 模式的密钥拼接可被长度扩展攻击** | `md5(paramsStr + "&key=" + secret)` 理论存在长度扩展风险（MD5/SHA1/SHA256 均受影响，SHA384/512 不受影响） | 新接入强制 `hmac-sha256`；存量 md5 逐步迁移 |

> R5 说明：长度扩展攻击在"密钥在末尾"的结构下难以直接利用（攻击者需构造 `paramsStr` 使拼接后碰撞），但这是该结构的理论弱点。HMAC 结构本身即为此设计。

### 8.2 功能限制

| # | 限制 | 说明 |
|---|------|------|
| L1 | 仅支持 Servlet 栈 | WebFlux 不装配（`@ConditionalOnWebApplication(SERVLET)`） |
| L2 | 仅支持 Boot 2.x / javax.servlet | Boot 3.x 用 `jakarta.servlet`，需改 import |
| L3 | JSON body 必须是对象 | 顶层数组/标量抛 12206 |
| L4 | body 上限 2MB 硬编码 | 大 payload 接口需改常量 |
| L5 | 嵌套深度 32 硬编码 | 同上 |
| L6 | 多值参数只取首值 | `values[0]`，其余值不参与签名 |
| L7 | 空字符串不参与签名 | 客户端传 `""` 与服务端不传等价，可能掩盖参数缺失 |
| L8 | 路径参数按段位比对 | URI 模板与 requestURI 段数不等时跳过（如含 `/**` 通配的匹配） |
| L9 | 不支持 content-type 为空的 JSON 请求 | `isJsonBody` 依赖 Content-Type，缺失则走参数模式 |

### 8.3 性能

| 项 | 成本 | 说明 |
|----|------|------|
| body 缓存 | 一次全量读入 + 2 倍内存 | 2MB 上限，JSON 请求 |
| 摘要计算 | MD5/SHA256 微秒级 | HMAC 略高，可忽略 |
| nonce 写入 | 内存 Map 或一次 Redis RTT | Redis 实现每请求多一次网络往返 |
| 密钥查询 | 默认 Map 查表 O(1) | 自定义 DB 实现**必须加缓存** |
| TreeMap 构造 | 每请求一次 O(n log n) | n = 参数个数，通常 < 20 |

### 8.4 并发与一致性

- `SignTemplate`、`SignParamResolver` 无请求态，单例安全
- `MemoryNonceStore` 用 `ConcurrentHashMap`，并发安全；但**单机**语义
- `RepeatableReadRequestWrapper` 单请求级别，每次 `getInputStream()` 新流，多线程读同一 request 场景不保证（Servlet 本身也不保证）

## 十、演进建议

| 方向 | 理由 | 优先级 |
|------|------|--------|
| `MemoryNonceStore` 启动时告警 | 多实例部署用内存实现等于无防重放，应在 `enabled=true` 且非单机时提示 | P0 |
| 把 `MAX_BODY_SIZE` / `MAX_FLATTEN_DEPTH` 提到 `SignProperties` | 硬编码导致大 payload 接口被迫改源码 | P1 |
| 支持 `excludeParams` | 当前只有 `includeParams` 白名单，网关追加字段场景用白名单更繁琐 | P1 |
| Boot 3.x 支持 | `jakarta.servlet` 分支，或抽取 servlet 适配层 | P2 |
| `SignClient` 抽独立 `Signer` | 当前用 `new SignTemplate(null)` 复用验签类，加签路径不访问 `NonceStore`，可用但取巧 | P2 |
| 提供 Micrometer 指标 | 验签失败率、非 12202 错误码占比，便于线上监控 | P2 |

> nonce 随机数已用 `SecureRandom`（`SignUtil.SECURE_RANDOM`），无需整改。
